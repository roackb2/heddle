# Heddle v5.9.0

Heddle v5.9 extends the public heartbeat SDK from managed polling to
request-driven and ephemeral workers. Hosts can route one durable task through
the standard claim-fenced execution pipeline, explicitly settle custom handler
work as retryable or blocked, and verify remote persistence adapters before
deploying them across workers. The terminal client also makes active work easier
to follow without changing the conversation runtime contract.

## Targeted heartbeat execution

- **`HeartbeatSchedulerService.runTask()` executes one routed task ID.** It
  performs direct lookup, durable eligibility checks, an atomic due claim, and
  claim-fenced settlement without scanning unrelated tasks or starting a
  scheduler loop.
- **Results are machine-readable.** Dispatchers can distinguish settled work,
  explicit handler retries, normal failures, missing, disabled, not-due, or busy
  tasks, lost claims, and cancellation without inspecting persistence records.
- **Host ownership stays explicit.** Queue delivery, tenant authorization,
  visibility timeouts, lease recovery, and domain-effect idempotency remain host
  responsibilities. A store claim fences duplicate execution settlement; it
  does not make external side effects exactly once.

## Custom handler outcomes

- **Handlers can reject a completed nested agent result deliberately.**
  `context.retry({ summary, delayMs })` records a bounded retry delay, while
  `context.block({ summary })` requires an explicit operator resume.
- **Checkpoint and ownership guarantees are preserved.** Retry and block use
  the same claim-fenced settlement path as built-in agent, skipped, failed, and
  cancelled outcomes, retaining the prior checkpoint and rejecting stale
  writes.
- **Operator summaries are bounded and durable.** Outcome summaries are
  normalized for control-plane projection and must not contain credentials,
  prompts, tokens, or domain payloads.

## Persistence confidence and examples

- **Remote adapters can run an opt-in conformance suite.** The
  `@roackb2/heddle/heartbeat/testing` entrypoint verifies exact lookup, atomic
  claims, coalesced run requests, settlement, recovery, and stale-write fencing
  across two adapter instances; history and subscriptions remain
  capability-gated.
- **The built-in file store serializes mutations per resolved heartbeat root.**
  Atomic file replacement and a shared in-process mutex protect task,
  checkpoint, and run-record transitions within one Node.js process. This is
  intentionally not a distributed lease.
- **A five-stage SDK path is now documented and executable.** Examples progress
  from one cycle through a long-lived worker, a domain handler, event-driven
  wake-up, and a targeted ephemeral worker, with host and Heddle ownership made
  explicit at every stage.

## Terminal client refinements

- Changed workspace files appear above Current Activity and use
  terminal-clickable paths.
- Submitted multiline prompts retain their line breaks in conversation history.
- The active plan is hidden as soon as final-response streaming begins, avoiding
  stale plan content beside the answer.

## Upgrade notes

- Install `@roackb2/heddle@5.9.0`.
  `@roackb2/heddle-remote@5.9.0` releases in lockstep.
- No persisted-data migration is required for the built-in file adapter.
- Existing scheduler and custom-runner APIs remain supported. The positional
  `HeartbeatTaskRunner` remains deprecated in favor of
  `HeartbeatTaskHandler` and `HeartbeatExecutionContext`.
- Replicated or ephemeral hosts need a remote `HeartbeatTargetedTaskStore` with
  atomic claim, fencing, and recovery semantics. Run the conformance suite, then
  separately validate the host's queue, lease, authorization, and idempotency
  policies.
